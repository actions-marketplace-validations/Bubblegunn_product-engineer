# product-engineer vs commitlint

commitlint checks that a commit message has the Conventional Commits shape. product-engineer checks that the message tells a non-technical reader what changed and why, and that it does not contradict the change. The two check different things and run together; product-engineer ships a commitlint plugin (`product-engineer/commitlint`).

## Same messages, same day

Twelve commit messages were given to both tools on 2026-10-20: product-engineer 0.6.2 and commitlint 21.2.4 with `@commitlint/config-conventional`. "flagged" means product-engineer reported an error or a warning, or commitlint exited non-zero. "cannot" means the tool is never shown the input that exposes the defect (commitlint reads a message, not a change). The tables are generated by `evals/comparison/render.mjs`; the full text with details is [`COMPARISON.md`](COMPARISON.md).

product-engineer won 6 cases, tied 3 and lost 3.

| message | product-engineer | commitlint |
|---|---|---|
| A full customer block | passed | passed |
| No customer block | flagged | passed |
| A heading with nothing under it | flagged | passed |
| A full block written in Turkish | passed | passed |
| Jargon in the block with no explanation | flagged | passed |
| Passing tests offered as the evidence | flagged | passed |
| A number with no method or scope | flagged | passed |
| Says tests were added; the change has none | flagged | cannot |
| A subject with no type | passed | flagged |
| A subject over 100 characters | passed | flagged |
| A body line over 100 characters | passed | flagged |
| A merge commit | passed | passed |

## Where product-engineer loses

The last three defect rows are commitlint's own job. A subject with no type, a subject over 100 characters and a body line over 100 characters are flagged by commitlint and passed by product-engineer, which has no check for them. Use commitlint for the Conventional Commits shape.

## What was not measured

Twelve messages is a small set chosen to cover each check once. It says which checks exist in which tool. It does not estimate how often either tool is right on messages from a real project. For product-engineer's own false-alarm rate on real messages, see [`evals/baseline/RESULTS.md`](../evals/baseline/RESULTS.md).

## Use both

Run commitlint in the commit-msg hook for the shape, and add the product-engineer rule through its plugin for the customer block. The commitlint setup is in [`install.md`](install.md) and `integrations/commitlint/README.md` in the repository.
